TASK 1 – Understand the Problem and Identify the Data1. Introduction and Problem ScenarioTwice a day, about 300 farmers bring milk to the Ksheera co-operative collection centre. The collection clerk records the volume in litres, fat percentage, and SNF (solids-not-fat) percentage for each farmer. Because manual or poorly written calculators cause paise-level discrepancies with bank statements and reject valid entries, we need to design a clean, accurate Python program that scales smoothly from 300 farmers up to 150,000 farmers at the district union level.2. Inputs and Outputs AnalysisInputs (Data we receive from the clerk):Farmer ID: Text or number (str or int) to uniquely identify each farmer.Litres: Quantity of milk supplied (float) – must be a positive number.Fat %: Fat content percentage (float) – determines quality adjustments.SNF %: Solids-not-fat percentage (float) – determines quality adjustments.Shift: Collection timing (str) – "Morning" or "Evening".Outputs (Data our program calculates):Rate per Litre: The final price calculated based on fat and SNF deviations from the standard.Amount Payable: Total money for a single collection entry (Litres $\times$ Rate per Litre).Ten-Day Total: Consolidated payment given to the farmer at the end of the 10-day cycle.3. Values That Never Change (Named Constants)To ensure that rate revisions can be made easily in one place, the following base rates and limits are defined as named constants (written in UPPER_CASE):BASE_RATE = 30.00 (Base price in Rupees for standard milk with 3.5% fat and 8.5% SNF)BASE_FAT = 3.5 (Standard fat percentage)BASE_SNF = 8.5 (Standard SNF percentage)FAT_STEP_VALUE = 0.40 (Rupees added or subtracted for every 0.1% change in fat)SNF_STEP_VALUE = 0.30 (Rupees added or subtracted for every 0.1% change in SNF)4. Classification of Data TypesWhole Numbers (int): Used for counting steps (e.g., number of 0.1% fat steps) and numeric Farmer IDs.Fractional Numbers (float / Decimal): Used for continuous measurements like litres, fat percentages, SNF percentages, rates, and money calculations.Text (str): Used for descriptive values like shift names ("Morning" / "Evening") and text-based IDs.5. Rules Every Correct Payment Must SatisfyPositive Quantity Rule: Milk quantity cannot be zero or negative (litres > 0).Fat Range Rule: Fat percentage must fall within allowed operational boundaries (typically between 2.0% and 7.0%).SNF Range Rule: SNF percentage must fall within allowed operational boundaries (typically between 6.0% and 12.0%).Currency Precision Rule: All final money outputs must be rounded accurately to 2 decimal places to match exact bank paisa amounts.6. Assumptions MadeEach farmer's shift entry is tested and recorded independently.Milk measurements provided by the automatic analyser have up to one or two decimal places of precision.Payout calculations are accumulated across the 10-day collection cycle.7. Alternative Concept & Complexity Analysis (Scalars vs. Lists)Design A (Using Separate Scalar Variables):
If we stored each farmer's record in individual variables (e.g., litres1, fat1, snf1, litres2, fat2, snf2... up to 300 farmers), the code would require hundreds of unstructured variables.Why it fails: It doesn't scale. Writing code for 300 variables is messy, and scaling it to block level (6,000 farmers) or union level (150,000 farmers) makes the program impossible to maintain.Design B (Using Lists/Tuples & Loops - Recommended):
Storing records inside collection structures allows us to process them using a simple loop.Time Complexity: To process $n$ entries, the time complexity is $O(n)$, meaning running time grows linearly and efficiently with data size.Space Complexity: The space complexity is $O(n)$ using lists or $O(1)$ if a running total is maintained on the fly. This design scales effortlessly from 300 to 150,000 farmers.
